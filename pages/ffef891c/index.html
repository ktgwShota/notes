リダイレクト用ページで起きる DOM XSS と open redirect

クエリで受け取った遷移先 URL を new URL() に通しただけで「URL として正しい」と扱うと、javascript: URL がそのまま通ります。そのページが遷移先を innerHTML に埋め込んだり location.href に代入したりしていれば、細工したリンクを踏ませるだけで、そのドメイン上で任意の JS を動かせます。

前提

「計測してから外部ページへ飛ばす」「数秒後に自動で遷移する」といった中継ページの話です。遷移先を ?redirect_url=... のようなクエリで受け取り、ブラウザ側の JS だけで処理するものを想定しています。

よくある実装

遷移先 URL をクエリから取り、「自動で遷移しない場合はこちら」というリンクを出し、一定時間後に遷移します。

const redirectUrl = new URL(params.get('redirect_url')).href

// 自動で遷移しないとき用のリンク
message.innerHTML = `遷移しない場合は <a href="${redirectUrl}">こちら</a>`

// 計測が遅れても待たせすぎないよう、5 秒後に必ず遷移する
setTimeout(() => { location.href = redirectUrl }, 5000)

// 計測が終わったら、http(s) のときだけ遷移する
if (/^https?:\/\//.test(redirectUrl)) {
  location.href = redirectUrl
} else {
  showError()
}

スキームの確認はありますが、最後の分岐にしかかかっていません。リンクとタイマーには、確認前の値がそのまま渡ります。

何が起きるか

同じ 1 つの値から、3 通りの問題が起きます。

  • innerHTML 経由ですぐに JS が動く redirect_url=javascript:"><img src=x onerror=...> を渡すと、" で href 属性を閉じて <img> を挿入できます。onerror はページを開いた瞬間に動き、クリックは要りません。
  • タイマー経由で数秒後に JS が動く location.href = 'javascript:...' はそのページの文脈で JS を実行します。エラー表示に切り替える処理があっても、setTimeout を解除していなければタイマーは残ったまま動きます。
  • 任意のサイトへ飛ばせる（open redirect） https:// で始まっていれば分岐も通るので、どこへでも遷移します。信頼されたドメインのリンクがフィッシングサイトの入口になります。

new URL() で防げない理由

new URL() は URL として解釈できるかを調べるだけです。安全な遷移先かどうかは判定しません。

  • javascript: は正しい URL URL Standard 上、javascript: は他のスキームと同じように有効です。例外は投げられず、protocol が "javascript:" の URL オブジェクトが返ります。
  • スキームによってエスケープされる文字が違う https: のような special scheme では、href にしたときパス・クエリ・フラグメントの " < > が percent-encoding されます。javascript: のパス部分は制御文字しかエスケープされないので、" < > がそのまま残ります。 
new URL('https://example.com/a"<>?q="<>').href
// => https://example.com/a%22%3C%3E?q=%22%3C%3E

new URL('javascript:"><img src=x onerror=alert(1)>').href
// => javascript:"><img src=x onerror=alert(1)>

https: だけを想定して試すと、" がエスケープされるので「属性は抜けられない」ように見えます。抜けられるのは javascript: のときだけなので、正常系のテストでは気づけません。

悪用されると何ができるか

攻撃者がやることは、細工したリンクをメールやメッセージで送ることだけです。

  • cookie を読む 親ドメイン（.example.com）に付いた cookie のうち、HttpOnly でないものは document.cookie で読めます。
  • 兄弟サブドメインに cookie を仕込む（cookie tossing） 静的ファイル用のサブドメインからでも、Domain=.example.com の cookie は書けます。管理画面など別のサブドメインに、セッション固定や CSRF トークンの上書きを仕掛けられます。
  • 信頼されたドメインで偽の画面を出す アドレスバーは本物のドメインのままなので、ログインフォームを描画すると見分けがつきません。
補足

「静的ファイルを置くだけのサブドメインだから」は安全の根拠になりません。cookie のスコープは親ドメイン単位で共有されるので、どれか 1 つのサブドメインで JS が動けば、他のサブドメインにも影響します。

どう直すか

入口で 1 回だけ検証し、通った値だけを後続に渡します。

  • スキームとホストを許可リストで照合する protocol === 'https:' に限り、hostname を許可リストと完全一致で比べます。前方一致や includes は example.com.evil.test のようなホストで突破されます。
  • HTML 文字列を組み立てない createElement('a') で要素を作り、a.href と textContent に代入します。属性値として扱われるので、" で抜ける余地がなくなります。
  • 失敗したらタイマーを止める エラー表示に切り替えるときは clearTimeout します。そもそも検証に通るまでタイマーを登録しない方が確実です。
  • CSP を付ける script-src を自ドメインに絞れば、インラインのイベントハンドラーや javascript: URL の実行をブラウザが止めます。静的ホスティングでも、CDN のレスポンスヘッダー設定で付けられます。検証漏れがあったときの保険です。 
const ALLOWED_HOSTS = ['example.com', 'www.example.com']

const parseRedirectUrl = (raw) => {
  if (raw === null) return null
  try {
    const url = new URL(raw)
    if (url.protocol !== 'https:') return null
    if (!ALLOWED_HOSTS.includes(url.hostname)) return null
    return url
  } catch {
    return null
  }
}

const redirectUrl = parseRedirectUrl(params.get('redirect_url'))
if (redirectUrl === null) {
  showError()
} else {
  const link = document.createElement('a')
  link.href = redirectUrl.href
  link.textContent = 'こちら'
  message.append('遷移しない場合は ', link)
  setTimeout(() => { location.href = redirectUrl.href }, 5000)
}

教訓

レビューで同じものを見逃さないための観点です。

  • 検証は使う場所ではなく入口に置く 値を使う場所（sink）が複数あると、どこか 1 つに検証を置いても他の経路が素通りします。検証済みの値しか存在しない状態を作れば、sink が増えても漏れません。
  • 「パースできた」と「安全」は別 new URL()、JSON.parse、型変換が成功しても、内容が想定内かは確認されていません。
  • URL を受け取る sink を覚えておく innerHTML だけでなく、location.href、location.assign、window.open、a.href、iframe.src も javascript: URL を実行します。a.href は HTML インジェクションは防げますが、スキームの検証はしてくれません。
  • 異常系の入力で試す URL を受け取る箇所は、https: の正常系に加えて javascript:、data:、許可外のホストでも動作を確認します。
