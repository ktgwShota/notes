url encoding

URL エンコードを二重にかけると文字列が変わる

encodeURIComponent は「この文字列がすでにエンコード済みか」を判定しません。% 自体がエスケープ対象なので、エンコード済みの文字列にもう一度かけると %3A は %253A になります。安全性は変わりませんが、値が変わるので比較や検索で一致しなくなります。

前提

percent-encoding（URL エンコード）の話です。encodeURIComponent / decodeURIComponent を例にしますが、同じ規則のエンコーダーなら言語を問わず同じことが起きます。

何が起きるか

1 回目で : が %3A になり、2 回目でその % が %25 になります。

元の文字列   https://example.com/path/あ
1 回目       https%3A%2F%2Fexample.com%2Fpath%2F%E3%81%82
2 回目       https%253A%252F%252Fexample.com%252Fpath%252F%25E3%2581%2582
  • 情報は失われない エンコードした回数だけ decodeURIComponent をかければ元に戻ります。2 回エンコードしたなら 2 回デコードです。
  • 回数が合わないと一致しない 読む側が「1 回エンコード済み」を前提に === や endsWith で比較すると、2 回エンコードされた値は別の文字列として扱われます。
  • 回数は値から判別できない %25E3 が「%E3 を 2 回エンコードしたもの」なのか「元から %25E3 という文字列」なのかは区別できません。書く側と読む側が回数を暗黙に共有する必要があります。
  • サイズが膨らむ % 1 文字が %25 の 3 文字になります。エンコード済み URL は % だらけなので、cookie の 4KB 上限のような制約があると効いてきます。

cookie 保存で起きやすい形

計測タグやセッション管理のスクリプトで、現在の URL を cookie に保存して次のページで比較するパターンを考えます。

  1. URL を取得した時点でエンコードしておく cookie の値には非 ASCII 文字や ; を入れられないので、encodeURIComponent(location.href) を保存用の値にします。ここまでは正しい対処です。
  2. cookie 書き込みの共通関数にもエンコードを足す 「どんな値が来ても安全にしたい」という動機で、書き込み関数の中でも encodeURIComponent をかけるようにします。すでにエンコード済みの値が渡ってくると、ここで二重になります。
  3. 読み取り側は変えない cookie を読んで endsWith(encodeURIComponent(location.href)) で「同じページか」を判定している処理は、%3A と %253A を比べることになり常に false になります。
補足

ブラウザは location.href や location.search を読むとき、URL 中の非 ASCII 文字を自動で percent-encoding します。一方 document.cookie への書き込みでは何もエンコードしません。「URL から取った値をデコードせずに cookie に入れている」場合だけ、URL 側のエンコードに乗っかって安全になっています。

検証コード

Node.js でそのまま実行できます。

const href = 'https://example.com/path/あ'

// URL 取得時に 1 回エンコード
const encodedUri = encodeURIComponent(href)
const sessionId = 'abc123XYZ0' + encodedUri

// cookie 書き込み側でもう 1 回エンコードしてしまった場合
const writtenToCookie = encodeURIComponent(sessionId)

console.log('1 回目      :', encodedUri)
console.log('cookie の値 :', writtenToCookie)
console.log('デコードなしで比較:', writtenToCookie.endsWith(encodedUri))
console.log('1 回デコードして比較:', decodeURIComponent(writtenToCookie).endsWith(encodedUri))
1 回目      : https%3A%2F%2Fexample.com%2Fpath%2F%E3%81%82
cookie の値 : abc123XYZ0https%253A%252F%252Fexample.com%252Fpath%252F%25E3%2581%2582
デコードなしで比較: false
1 回デコードして比較: true

どう避けるか

エンコードは 1 回だけ、どこでやるかを決めておく、が原則です。

  • エンコードする場所を 1 箇所に決める 「値を取得した時点」か「保存する直前」のどちらかに統一します。両方でやると必ず二重になります。
  • 書き込みでエンコードするなら読み取りでデコードする 保存関数でエンコードする設計にするなら、読み取り関数で decodeURIComponent して対称にします。不正な % で URIError が出るので、try/catch で生の値にフォールバックしておきます。
  • 既存データとの整合を確認する すでに保存されている値のエンコード回数が変わると、デプロイ後の最初の読み取りで一致しなくなります。cookie の有効期限内は古い形式の値が残ることを前提に影響を見積もります。
