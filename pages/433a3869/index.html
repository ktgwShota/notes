build reproducibility

ts-loader は最初に処理したファイルの場所で tsconfig を決める

ts-loader は configFile を指定しないと、最初に処理した .ts ファイルのディレクトリから tsconfig.json を探し、見つけた設定をそれ以降のすべてのファイルに使います。webpack のエントリが複数あると、どのファイルが先に届くかはビルドのたびに変わります。そのため、同じコミットから target の違う成果物ができることがあります。

前提

webpack + ts-loader で、ディレクトリごとに別の tsconfig.json を置いている構成の話です。ts-loader 9 系のソースで挙動を確認しています。

何が起きるか

次のように、2 つのエントリが別々の tsconfig.json の下にあり、1 つの webpack 設定でまとめてビルドしている場合です。

.
├── src/
│   ├── tsconfig.json     // target: es2017
│   └── main.ts
├── tools/
│   ├── tsconfig.json     // target: es2022
│   └── index.ts
└── webpack.config.js
module.exports = {
  entry: {
    main: './src/main.ts',
    tool: './tools/index.ts',
  },
  module: {
    rules: [{ test: /\.ts$/, use: 'ts-loader' }],
  },
}
先に届いたファイル 使われる tsconfig 出力
src/main.ts 想定どおりの回。main も tool も es2017 に変換されます。
src/
es2017
tools/index.ts main まで es2022 で出力されます。?.、??、クラスフィールドが変換されずに残ります。
tools/
es2022

es2022 の出力は、クラスフィールドを解釈できないブラウザでは SyntaxError になり、ファイル全体が動きません。ビルドは成功し、新しいブラウザでは問題なく動きます。そのため、何回かに 1 回だけ古いブラウザで動かない成果物が出る状態になります。

なぜ起きるか

tsconfig の探し方と、見つけた設定のキャッシュの仕方の組み合わせで起きます。

  • 探索の起点は、そのとき処理しているファイル configFile がなければ、処理中の .ts ファイルのディレクトリから親へたどって tsconfig.json を探します。webpack.config.js の場所やカレントディレクトリは使われません。
  • 見つけた設定は使い回される ts-loader は TypeScript のコンパイラインスタンスを、webpack のコンパイラと instance オプションの組でキャッシュします。tsconfig を探すのはインスタンスを作るときの 1 回だけなので、最初のファイルで決まった設定がほかのファイルにも適用されます。
  • エントリを処理する順序は決まっていない webpack は複数のエントリを並行して解決します。ファイルの読み込みやモジュール解決の速さしだいで、どちらが先にローダーに届くかが変わります。
  • 相対パスで指定しても揺れる configFile: './tsconfig.json' のような相対パスは、処理中のファイルのディレクトリを基準に解決されます。起点が揺れるので、指定しない場合と同じことが起きます。

気づきにくい理由

ビルドのログにも、手元の動作確認にも出てきにくい問題です。

  • エラーにも警告にもならない どちらの tsconfig も正しい設定なので、ビルドは毎回成功します。違うのは出力の構文だけです。
  • 新しいブラウザでは差が出ない 開発者が普段使うブラウザは es2022 を解釈できるので、どちらの成果物でも動きます。
  • 同じ環境でも結果が変わる 手元で 1 回ビルドして確かめても、もう片方の出力を見ていないだけかもしれません。CI でも、デプロイのたびにどちらになるかが変わります。

どう防ぐか

使う tsconfig をファイルの処理順に依存させないことと、成果物の構文を検査することの 2 つです。

  • configFile を絶対パスで指定する path.resolve(__dirname, ...) で絶対パスにすれば、どのファイルが先に届いても同じ tsconfig が使われます。
  • 設定を分けたいなら、インスタンスを分ける エントリごとに別の tsconfig を使いたい場合は、webpack の設定を配列にしてコンパイラを分けます。1 つの設定のままなら、include でディレクトリを分けたルールを作り、それぞれに別の instance 名と configFile を指定します。
  • 成果物の構文レベルを CI で検査する es-check などで、ビルド後のファイルが想定した ECMAScript のバージョンで構文解析できるかを確かめます。ソースの設定ではなく成果物を見るので、原因がどこにあっても検出できます。
  • 同じコミットを何回かビルドして比べる 成果物のハッシュが毎回一致するかを確かめると、こうした揺れがあることに気づけます。ビルドの設定を変えたときの確認として有効です。 
const path = require('path')

module.exports = {
  entry: {
    main: './src/main.ts',
    tool: './tools/index.ts',
  },
  module: {
    rules: [
      {
        test: /\.ts$/,
        use: {
          loader: 'ts-loader',
          options: { configFile: path.resolve(__dirname, 'src/tsconfig.json') },
        },
      },
    ],
  },
}
npx es-check es2020 './dist/**/*.js'
