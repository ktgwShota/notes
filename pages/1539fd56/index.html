character encoding

UTF-8 の JS を Shift_JIS のページで読むとテンプレートリテラルが壊れる

配信時に charset を指定していないスクリプトを、ブラウザは埋め込み先のページの文字コードで読みます。UTF-8 の日本語を Shift_JIS として読むと、日本語の直後にあるバッククォートが前の文字に取り込まれて消えることがあります。テンプレートリテラルが閉じなくなるので、スクリプト全体が構文エラーで動かなくなります。

前提

計測タグやウィジェットのように、他人のサイトに <script src> で埋め込まれるスクリプトの話です。埋め込み先のページの文字コードは選べず、Shift_JIS や EUC-JP のページもまだ残っています。

何が起きるか

UTF-8 で書いたスクリプトを、Shift_JIS のページから読み込んだ場合です。

// UTF-8 で書いたソース
const a = `処理を開始`
const b = "次の処理"

// Shift_JIS として読まれたソース
const a = `蜃ｦ逅�ｒ髢句ｧ義
const b = "谺｡縺ｮ蜃ｦ逅�"
// => SyntaxError: Unexpected end of input

閉じのバッククォートが「義」に取り込まれて消えています。テンプレートリテラルはファイルの末尾まで閉じないので、エラーはそのファイル全体に及びます。どこか 1 箇所が壊れるだけで、そのスクリプトは何も実行されません。

同じ文字列をシングルクォートで書いた場合は、文字化けはしますが構文エラーにはなりません。

const a = '蜃ｦ逅�ｒ髢句ｧ�'   // 化けるが、文字列としては閉じている

なぜ起きるか

文字コードの決まり方と、Shift_JIS のバイトの区切り方の組み合わせで起きます。

  • スクリプトの文字コードはページから引き継がれる ブラウザは BOM、レスポンスの Content-Type の charset、<script> の charset 属性の順に文字コードを探します。どれもなければ、読み込んだページの文字コードを使います。Content-Type: text/javascript だけでは charset がないので、Shift_JIS のページからは Shift_JIS として読まれます。
  • Shift_JIS の 2 バイト目には ASCII の範囲も含まれる Shift_JIS の 2 バイト文字は、2 バイト目に 0x40〜0x7E と 0x80〜0xFC を使います。UTF-8 の日本語の末尾のバイトが Shift_JIS の 1 バイト目として読まれると、直後の ASCII 文字が 2 バイト目として取り込まれます。
  • バッククォートは取り込まれる範囲にある バッククォートは 0x60 です。開始` は UTF-8 で E9 96 8B E5 A7 8B 60 になり、最後の 8B 60 が 1 文字として読まれます。シングルクォート（0x27）とダブルクォート（0x22）はこの範囲の外なので、取り込まれません。
  • 壊れるかどうかは前にある文字で変わる バイトがどこで区切られるかは、それより前のバイト列で決まります。`開始` は壊れますが、`停止` や `送信しました` は壊れません。同じパターンの書き方でも文言しだいで壊れたり壊れなかったりするので、コードを見ただけでは気づけません。

取り込まれる ASCII 文字

0x40〜0x7E に入る記号は次のとおりです。日本語の直後に来ると消える可能性があります。

@ [ \ ] ^ _ ` { | } ~  と英字（A〜Z, a〜z）
  • 構文が壊れる テンプレートリテラルを閉じるバッククォートと、正規表現リテラルの文字クラスを閉じる ]。/[０-９]/ は「９」の最後のバイトが ] を取り込み、Invalid regular expression になります。どちらもファイル全体が構文エラーになります。
  • 意味が変わる バックスラッシュ（0x5C）。'あ\n' の \ が消えると、改行ではなく n という文字になります。構文エラーにならないので、さらに気づきにくくなります。
  • 影響しない ' " $ ( ) , ; は範囲の外です。文字列の中身が化けるだけで、コードの構造は保たれます。

どう防ぐか

「文字コードを配信側で決める」か「ファイルを ASCII だけにする」のどちらかで、埋め込み先の文字コードの影響を受けなくなります。両方やっておくと確実です。

  • Content-Type に charset を付けて配信する Content-Type: text/javascript; charset=utf-8 にすれば、ページの文字コードに関係なく UTF-8 で読まれます。オブジェクトストレージや CDN から配信している場合、拡張子から推測される Content-Type には charset が付かないことが多いので、アップロード時やレスポンスヘッダーの設定で明示します。
  • ビルド時に非 ASCII 文字をエスケープする 日本語を 開始 のような形にしておけば、ファイルは ASCII だけになり、どの文字コードで読まれても同じ内容になります。terser なら format.ascii_only: true で有効になります。esbuild は既定で ASCII だけを出力します。
  • Shift_JIS のページで読み込むテストを置く <meta charset="Shift_JIS"> のページでビルド後のスクリプトを読み込み、エラーが出ないことを確かめます。壊れるかどうかは文言しだいなので、レビューで見つけるのではなく機械的に検出します。
補足

<script charset="utf-8"> でも文字コードは指定できますが、埋め込む側に書いてもらう必要があり、HTML の仕様でも非推奨です。他人のサイトに配るスクリプトでは、配信側で決める方法を使います。壊れた箇所だけをクォートの文字列連結や \u{FF10} のようなエスケープに書き換えても、同じ書き方が別の場所に入れば再発します。文字化けとバックスラッシュの問題も残ります。

手元で確かめる

ビルド済みのファイルを Shift_JIS として読み直し、構文として成り立つかを Node.js で確認できます。

const fs = require('fs')

const source = fs.readFileSync(process.argv[2])
const asShiftJis = new TextDecoder('shift_jis').decode(source)

try {
  new Function(asShiftJis)
  console.log('Shift_JIS で読んでも構文エラーにならない')
} catch (error) {
  console.log('Shift_JIS で読むと壊れる:', error.message)
}
